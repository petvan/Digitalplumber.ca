Tracing agent tool calls catches failures metrics miss

Last9 published a technical guide on instrumenting AI agents for observability, addressing the gap between LLM call monitoring and agent workflow tracing. The guide details what practitioners need to trace in autonomous agents: tool calls, reasoning steps, and handoffs—not just tokens and latency—to catch wrong-tool hallucinations, bad context handoffs, and looping agents invisible in aggregate metrics.

Last9 Blog · Sep 22, 2026

Last9 · Agent Observability · OpenTelemetry · AI Agents · MCP

Last9's practitioner guide distinguishes agent observability from LLM observability: a single LLM call only reveals tokens, latency, and cost, but an autonomous multi-step agent can return 200 status, finish in normal time, and still have called the wrong tool, hallucinated an argument, or handed off corrupted context to the next step. The agent-span model (in OpenTelemetry specification development status as of 2026) traces tool calls, reasoning steps, and handoffs as separate instrumentation points. W3C Trace Context propagation links MCP server spans as children of client spans, keeping tool calls traceable end-to-end even when tools run as separate services. The guide flags repeated production patterns: looping (agents retrying without progress, invisible in aggregate metrics); missing context (agents handling a task without the information needed); and hallucinated arguments (models inventing parameters). This is foundational knowledge for teams deploying Last9's MCP server (which connects Claude, Cursor, Windsurf directly to production telemetry) or building custom SRE copilots and incident bots. The article emphasizes that agent-span attribute names remain in flux, so practitioners should validate against the current OpenTelemetry specification before building dashboards.

1.6T OSFP optics enter customer validation ahead of production

The OSFP form factor is actively evolving to support 1.6 Tbps using 8 × 200G PAM4 electrical lanes, with engineering samples already in customer validation and volume production expected in late 2026 through 2027. Next-generation 102.4 Tbps platforms such as Broadcom Tomahawk 6 and Cisco Silicon One G300 are designed around 200G-class SerDes and 1.6T ports. This milestone marks the transition from roadmap to production-ready infrastructure.

Robotics and Automation News · Sep 22, 2026

1.6T Ethernet · OSFP · Optical Transceiver · GPU Training · Broadcom Tomahawk

OSFP 1.6 Tbps modules use 8 × 200G PAM4 electrical lanes, with engineering samples in customer validation and volume production targeted for late 2026–2027. AI training infrastructure is the single largest driver of OSFP adoption in 2026, as bandwidth demands of large GPU clusters cannot be met with lower-speed optics without exploding switch counts and oversubscription ratios. The practical impact is immediate: each DGX B200 GPU demands 400 Gbps of host-side connectivity, and a single DGX B200 system with eight GPUs requires 3.2 Tbps of aggregate uplink bandwidth—consuming eight leaf switch ports at 400G per port. Switch silicon suppliers including Broadcom (Tomahawk 6) and Cisco (Silicon One G300) have already designed 102.4 Tbps platforms around 200G-class SerDes and 1.6T ports. For network operators, this signals that 1.6T optics transition from experimental to standard-path procurement by Q4 2026, requiring fiber plant and transceiver inventory planning now.
