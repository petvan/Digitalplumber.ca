BGP maximum-prefix limits are disconnecting networks that grow

Internet Society · Nov 11, 2026 · Analysis

Internet Society research shows maximum-prefix limits on BGP sessions, designed to prevent route leaks, inadvertently disconnect networks when they legitimately grow their route announcements. The study found outages ranging from minor disruption to loss of over 80% of peers including Tier-1 providers.

Why it matters Network operators must tune prefix limits dynamically, not statically; organic growth can trigger false alarms that look identical to route leaks in your monitoring.

The maximum-prefix limit is a safety mechanism set during BGP configuration that acts like a circuit breaker: if a peer sends more routes than agreed, the session drops. Originally intended to protect against route leaks and router memory overload, this protection sometimes activates for legitimate reasons. The Internet Society's study examined how networks growing their announcements—a normal operational change—can inadvertently hit preset safety limits and disconnect from peers entirely. The trigger mechanism tracks peers that send unexpectedly high route counts, with operational costs ranging from minor disruption to loss of over 80% of peers, including Tier-1 and major providers. The case of Optus showed how critical this safety switch can be, but the research also demonstrates that it trips for ordinary operational reasons. This means the limit is only effective if kept in sync with actual network growth, requiring either manual tuning or automation to adjust thresholds.

RFC 10082 standardises composite ML-DSA signatures for CMS

RFC Editor / IETF · Nov 7, 2026 · Primary source

IETF publishes RFC 10082, standardizing hybrid post-quantum signatures using Composite ML-DSA (Module-Lattice-Based DSA) in Cryptographic Message Syntax (CMS) for S/MIME, code signing, and document signing. Pairs ML-DSA with RSA, ECDSA, or EdDSA for backward-compatible hybrid protection.

Why it matters Security and infrastructure teams must begin implementing hybrid ML-DSA signatures in certificate and S/MIME workflows; this standard enables gradual migration to post-quantum cryptography without breaking compatibility with deployed systems.

RFC 10082 is a Standards Track Proposed Standard (companion to RFC 10073, which covers X.509 certificates) that enables organizations to deploy hybrid signatures combining post-quantum ML-DSA with classical algorithms. The RFC defines four hybrid pairings: ML-DSA-44+RSA-2048-PSS (SHA-256), ML-DSA-65+ECDSA-P-256 (SHA-512), ML-DSA-65+Ed25519 (SHA-512), and ML-DSA-87+Ed448 (SHAKE256). Each pairing specifies the digest algorithm and CMS encoding. ML-DSA (defined by NIST in FIPS 204) is designed to resist cryptographically relevant quantum computers (CRQCs). By combining ML-DSA with proven classical signatures in hybrid form, organizations achieve quantum-resistance today while maintaining compatibility with systems that do not yet support ML-DSA alone. CMS (RFC 5652) is used in S/MIME email, code signing (e.g., Java, .NET code objects), document signing (PDF, Office), and certificate signing requests. RFC 10082 allows SignedData structures to carry composite signatures via new algorithm OIDs, enabling seamless deployment in existing PKI workflows. Operators should coordinate certificate issuance policies, S/MIME client support (Outlook, Apple Mail, Thunderbird), and code-signing toolchains to roll out composite signatures. NIST's FIPS 204 and RFC 10082 represent the first standardized post-quantum signature algorithms suitable for broad cryptographic use, making this a critical infrastructure transition point.
