Nautobot alpha loosens primary IP interface assignment requirement

Nautobot (GitHub/PyPI) · Nov 13, 2026 · Primary source

Nautobot released v3.3.0a2 alpha on Nov 13, 2026, adding PRIMARY_IP_REQUIRES_INTERFACE_ASSIGNMENT configuration setting. When disabled, allows IP addresses not assigned to any interface to be designated as primary IP for Devices, Virtual Machines, or VDCs.

Why it matters Configuration flexibility enables automation of overlay and virtual infrastructure models where primary IPs can float independent of physical interface state; reduces constraints on intent-based network automation patterns.

v3.3.0a2 alpha introduced PRIMARY_IP_REQUIRES_INTERFACE_ASSIGNMENT configuration setting; when disabled, an IP address that is not assigned to any interface can be designated as the primary IP of a Device, Virtual Machine, or Virtual Device Context. This change supports modern network designs using floating IPs, virtual addresses, and overlay networking where primary IP semantics decouple from physical interface membership. Release v3.2.9 (also Nov 9, 2026) fixed Device LLDP Neighbors tab database query performance regression by eliminating per-interface queries when rendering connected endpoints. These are pre-release (alpha) versions available on PyPI; stable v3.2.9 remains the production release. The timing aligns with NautoCon Tucson (Nov 18, 2026) where customer panel from ONEOK, Microsoft, and Fidelity will share production Nautobot operational patterns.

Broadcom pitches disaggregated Ethernet fabric against Cisco Silicon One

IEEE ComSoc Blog · Nov 16, 2026 · Analysis

Broadcom unveiled its open Ethernet fabric portfolio at SC26, contrasting its disaggregated ASIC strategy (Tomahawk Ultra, Tomahawk 6, Jericho 4 paired with Thor Ultra NICs) against Cisco's unified P4-programmable Silicon One architecture for AI workloads.

Why it matters Clarifies architectural divergence in 102.4T switching: disaggregated ASICs versus unified silicon affects tail-latency behavior, fabric programmability, and multi-vendor interoperability for large AI clusters.

Broadcom's SC26 presentation highlighted two competing 102.4 Tbps switching architectures: Broadcom's specialized chipsets (Tomahawk 6 for spine/fabric, Jericho 4 for disaggregated leaf) paired with Thor Ultra NICs, versus Cisco's unified Silicon One G300 architecture. The architectural choice affects congestion management: Broadcom relies on AI-optimized ASICs with cognitive routing, while Cisco embeds Intelligent Packet Flow—absorbing all-reduce micro-bursts directly in Silicon One's on-die packet buffers with real-time fabric telemetry to steer flows. For RoCEv2 deployments, Cisco claims 33% better network utilization; Broadcom emphasizes supplier flexibility and ecosystem choice. Both ship 1.6T-ready silicon in production. For practitioners, the choice maps to procurement philosophy: Broadcom appeals to white-box operators and hyperscalers who want component fungibility; Cisco targets enterprises seeking an integrated platform with unified telemetry and P4 programmability.

Arista launches R4 routers for edge AI inferencing

Communications Today · Nov 18, 2026 · Industry news

Arista unveiled R4 routers—compact, hardened access routers, coherent transport router, and 25.6-Tbps pluggable optical line system—designed for distributed AI inferencing at hyperscalers and neocloud operators needing 1.6T links with liquid cooling.

Why it matters Extends AI networking from data-center spine-leaf to metro/edge; enables neoclouds and hyperscalers to link 100k-1M accelerator clusters across multiple facilities with native 1.6T interconnect.

Arista positioned its R4 router family to bridge the gap between in-cluster (100k–1M accelerators) and inter-cluster networking. The R4 targets two customer segments: hyperscalers and neoclouds running 100k+ accelerator clusters across multiple data centers requiring 1.6-terabit links with liquid cooling, and enterprises deploying smaller clusters (500–1k accelerators) over air-cooled, lower-speed links. The launch includes Broadcom Jericho-based hardware in form factors suited to metro and carrier deployments, integrated with Arista's EOS operating system. The R4 leverages Arista's cloud routing track record to offer operational consistency for customers already running EOS. This is strategically significant: Cisco, HPE Juniper, and Nokia will pursue the same opportunity, but Arista is claiming first-mover advantage on turning cloud routing into metro/carrier production wins. For practitioners building distributed AI infrastructure, this signals that metro interconnect for AI is moving from proprietary coherent solutions to standard, Ethernet-based, software-driven platforms.

Critical OpenSSL Base64 overflow waits for December fix

CyberSecurityNews · Nov 20, 2026 · Industry news

A critical CVSS 9.8 heap buffer overflow in OpenSSL's Base64 encoding function (CVE-2026-121481, published November 18, 2026) can corrupt application memory when processing very large inputs. Fixed versions 4.0.4 and 4.1.1 are scheduled for December 1, 2026.

Why it matters No known exploitation or CISA KEV entry exists as of November 19, but widespread OpenSSL usage in TLS implementations across network infrastructure makes this high-priority for pre-patch staging before December release.

The vulnerability is a heap buffer overflow in OpenSSL's Base64 encoding function that can corrupt application memory when the library processes very large inputs. This affects the fundamental cryptographic library underpinning TLS in millions of network devices, load balancers, VPNs, and API gateways. While no known exploitation or CISA KEV entry exists as of November 19, the December 1 release window leaves a narrow patching window before widespread adoption of fixed versions. Network teams running inline encryption, SSL inspection, or VPN termination should audit their OpenSSL versions immediately: affected versions include OpenSSL 3.x and 4.x across multiple release lines. Organizations should plan patch testing now to avoid December emergency patching cycles. The bug resides in the encoding path, so systems performing Base64 operations on large payloads—common in API gateways and content filters—are at highest risk.

BGP draft would signal multiple next hops per route

IETF IDR Working Group · Nov 19, 2026 · Primary source

Updated draft of BGP MultiNexthop Attribute extends BGP to signal multiple next hops per route with per-nexthop constraints (proximity, transport class, load balance). Version 06 updated November 19, 2026.

Why it matters Enables explicit multi-path steering and nexthop-specific constraints in BGP; operationally relevant for load balancing, segment routing integration, and service function chaining without requiring separate signaling protocols.

Draft-ietf-idr-multinexthop-attribute-06, updated 2026-11-19, formalizes a BGP attribute allowing a single NLRI to carry multiple next-hop addresses with per-nexthop constraints. Key constraint types include proximity checks (single-hop vs multihop flags), transport class ID (color-based routing integration), and load balance factors (percentage-based traffic split). The attribute solves operational problems with multihomed PEs, label oscillation, and forwarding loops in complex topologies. For network operators, this draft enables richer traffic engineering policies directly in BGP without requiring separate MPLS or Segment Routing channels. The mechanism integrates with Flowspec and BGP Label Unicast. Expected to progress toward WGLC at IETF 127 (Nov 2026); early implementation in test labs recommended for operators planning multi-vendor TE deployments.

New BGP Flow-Spec draft adds payload compression action

IETF IDR Working Group · Nov 16, 2026 · Primary source

New draft proposes BGP Flow-Spec extension allowing headend routers to compress packet payloads based on Flow-Spec match rules. First version published November 16, 2026.

Why it matters Adds compression-as-a-service capability to Flow-Spec; reduces backbone link utilization for compressible traffic (logs, text) without requiring separate middleboxes; operationally useful for cost reduction on expensive leased circuits.

Draft-ietf-idr-flowspec-traffic-compress-action-00 introduces a new BGP Flow-Spec extended community that signals compression algorithms to be applied by headend routers. For packets matching a Flow-Spec rule that are not already compressed, the headend compresses the payload using the indicated algorithm and encapsulates the result. The mechanism applies to uncompressed packets only, avoiding redundant compression. This draft addresses operational scenarios where certain traffic classes (application logs, telemetry, uncompressed video) can be reduced 30–70% in size, directly impacting WAN link utilization metrics. For network operators with constrained backbone capacity, this avoids costly provisioning upgrades by offloading compression to the data plane. Processing overhead and hardware support (must be vendor-specific) are open implementation questions. Early feedback from vendor implementations likely needed before this advances.
