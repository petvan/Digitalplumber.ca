Oracle ships collective communications library that reroutes around NIC failures

SDxCentral · Nov 11, 2026 · Industry news

Oracle released OCCL, a network plugin dedicated to distributed AI training preinstalled in supported Oracle HPC images. OCCL automatically reroutes traffic around link or NIC failures and supports single-planar and multi-planar RDMA networks.

Why it matters Benchmarks on NVIDIA GB300 systems show OCCL increased average NCCL bus bandwidth by 2-10% for AllReduce operations, reducing collective communication latency across large distributed AI clusters.

Oracle announced new capabilities in Oracle Acceleron, OCI's suite of networking and infrastructure technologies for demanding AI workloads. OCCL sits at the transport layer between the collective-communication library (NCCL/RCCL) and the underlying network fabric, implementing congestion control and link/NIC failure recovery without requiring changes to higher-level AI frameworks. Internal benchmarks using NVIDIA GB300 systems with 16-128 nodes and four GPUs per node showed OCCL increased average NCCL bus bandwidth by 2-10% for AllReduce operations. This addresses a critical operational challenge: a one-second network delay across 100,000 GPUs could waste 28 hours of aggregate processing time. For operators running distributed training at scale, the plugin provides automatic failover and congestion intelligence without requiring fabric redesign.

SonicWall SSL-VPN MFA bypass under active exploitation

CISA Known Exploited Vulnerabilities Catalog · Nov 6, 2026 · Primary source

CISA added CVE-2026-19868 (SonicWall SonicOS SSLVPN authentication bypass) to Known Exploited Vulnerabilities on November 6, 2026, based on evidence of active exploitation. Flaw allows attackers with valid alternate credentials to bypass SAML-enforced multi-factor authentication.

Why it matters SonicWall SSLVPN gateways are internet-facing remote-access devices. MFA bypass on production VPN infrastructure enables direct path to lateral movement. CISA deadline November 20, 2026 for federal agencies.

CVE-2026-19868 is an authentication enforcement flaw exploitable only when SAML is enabled for SSL-VPN logins. CWE-308: Use of Single-factor Authentication. CVSS 7.1 High. Fixes in SonicOS 7.3.4-7013 and 8.2.3-8015. Affects Gen7 and Gen8 firewalls. No public IoCs or detailed attack analysis published yet. Network teams must inventory SonicWall Gen7/Gen8 SSL-VPN deployments, prioritize SAML-enabled configuration patching, and monitor authentication logs for non-SAML logins to SAML-protected portals.

OpenSSL patches DTLS and AES-GCM-SIV cryptographic flaws

OpenSSL Security Advisory / SUSE Security Updates · Nov 11, 2026 · Primary source

OpenSSL November 2026 advisory disclosed multiple cryptographic flaws including CVE-2026-88823 (AES-GCM-SIV Additional Authenticated Data handling), CVE-2026-84782 (DTLS retransmits from stale buffer, CVSS 8.2 High), and CVE-2026-35189 (excessive memory allocation in CRL processing, CVSS 5.3 Medium). Affects OpenSSL 3.5, 4.0, and 4.1 versions.

Why it matters OpenSSL is foundational cryptographic library in network infrastructure, TLS implementations, VPNs, and appliances. CVE-2026-84782 rated High with potential for denial of service or information disclosure in DTLS-based protocols. SUSE issued high-severity livepatches November 11, 2026.

CVE-2026-88823: AES-GCM-SIV implementation treats zero-length AAD update as reset instead of no-op, causing previous AAD chunks to become unauthenticated (CWE-325). CVE-2026-84782: DTLS retransmission handler may use stale buffer for handshake messages, rated 8.2 High by SUSE. CVE-2026-35189: Certificate with many nameRelativeToCRLIssuer CRL distribution points causes disproportionate heap growth when OpenSSL caches X.509 extensions, rated 5.3 Medium. FIPS modules not affected; vulnerabilities in default provider only. Infrastructure teams must update OpenSSL to 3.5.10, 4.0.4, or 4.1.1+.

Isolated telecom AI agents make conflicting decisions during outages

RCR Wireless News · Nov 12, 2026 · Analysis

Telecom operators deploy isolated AI agents across network operations, customer care, and planning, creating conflicting decisions. In a fiber-cut scenario, network ops reroutes traffic while customer care, unaware, issues credits and books technicians because systems describe inventory differently.

Why it matters Shared operational context enabling agents to see each other's work before acting is essential for credible cross-business autonomous operations; agent orchestration, not isolation, drives value.

Telecom operators have moved quickly to deploy AI agents in network operations, customer care, and capacity planning, with most performing well independently. However, isolated agent systems create operational conflict: in a metro fiber cut, the network operations agent reroutes traffic within seconds while the customer care agent, unaware of the fix, issues service credits and books technicians. Network inventory, customer records, and planning tools describe the same resources differently, preventing AI agents from recognizing they are working on the same problem.

The core issue is semantic fragmentation: without unified context, independent agents optimize locally while creating downstream chaos. The author advocates connecting network events to affected customers and enabling agents to see each other's work before acting. This shared understanding goes well beyond agents passing messages and represents what makes autonomous operations credible across the business. Multi-agent orchestration through unified data models or MCP-based coordination is necessary for telcos to achieve end-to-end autonomous operations.

IETF publishes multipath QUIC as RFC 10069

IETF RFC Editor · Nov 7, 2026 · Primary source

IETF published RFC 10069 defining multipath support for QUIC, enabling connection migration and load distribution across multiple network paths. Specifies IP addressing and routing architecture for multipath QUIC endpoints.

Why it matters Multipath QUIC reduces latency and improves resilience for high-performance applications; network operators must plan path diversity and congestion control for endpoints using this RFC.

RFC 10069, published November 7, 2026, formalizes multipath operation in QUIC (Quick UDP Internet Connections). The specification allows a single QUIC connection to span multiple network paths simultaneously, enabling seamless handover between paths, load balancing across interfaces, and recovery from path failures without connection disruption. Key aspects include path validation mechanisms, congestion control coordination across paths, and connection ID usage for path identification. This is particularly relevant for operators managing high-availability infrastructure and those deploying QUIC-based services where connection resilience is critical. The RFC draws distinctions between active multipath usage (simultaneous transmission) and migration scenarios (switching paths). Network teams should review implications for traffic engineering policies, especially regarding packet reordering and out-of-order delivery handling on multi-path flows.

OpenConfig moves tunnel and VLAN config to subinterface level

OpenConfig GitHub · Nov 5, 2026 · Primary source

OpenConfig released updates to tunnel interface and VLAN YANG models (versions 0.2.0 and 3.3.0) moving configuration to subinterface level and deprecating interface-level containers. Improves structural consistency and future model evolution.

Why it matters Network automation engineers must migrate configurations from interface-level to subinterface-level tunnel and routed-VLAN containers before deprecated paths are removed; affects Ansible, gNMI, and YANG-driven provisioning workflows.

OpenConfig published updates on November 5, 2026 to openconfig-if-tunnel.yang (v0.2.0) and openconfig-vlan.yang (v3.3.0) via GitHub PR #1602. The changes relocate tunnel configuration from interface level to subinterface level for tunnel-type interfaces, and routed-vlan configuration to subinterface level for l3ipvlan types. Legacy interface-level containers are marked deprecated, signaling removal in future releases. Rationale centers on structural consistency: subinterfaces already support protocol stacking (IPv4, IPv6, MPLS), so tunnel and VLAN bindings logically belong there. This affects network automation teams using these models for device configuration. Migration path: dual-support via feature gates allows parallel naming conventions during transition. For operators, this requires updating YANG-based configuration generators, validating data model validators against new structure, and testing with devices that enforce new schema. The changes maintain backward compatibility during the deprecation window but require proactive migration of infrastructure-as-code.
