Attackers exploit Cisco ASA and FTD VPN zero-day

Cisco Security Advisory / CISA · Oct 28, 2026 · Vendor release

Cisco disclosed CVE-2026-76418, a high-severity zero-day in Cisco Secure Firewall ASA and FTD Remote Access SSL VPN service, after PSIRT became aware of active exploitation in October 2026. The flaw allows unauthenticated remote attackers to trigger device reloads, causing denial-of-service conditions affecting VPN availability.

Why it matters Over 51,000 ASA SSL VPN devices remained internet-exposed—firewall teams must immediately patch or disable secondary authentication on internet-facing tunnel groups; no workaround exists except patching.

An unauthenticated remote attacker exploits CVE-2026-76418, a logic error in ASA/FTD SSL VPN secondary authentication handling, by sending a crafted request to internet-exposed webvpn interfaces, forcing targeted firewall devices to reload and disrupting availability. Cisco published its advisory on October 28, 2026, assigning the vulnerability a CVSS score of 8.6. CISA added it to its Known Exploited Vulnerabilities (KEV) catalog on October 29, with a federal remediation deadline of November 1, 2026. Cisco has confirmed in-the-wild exploitation during October but has not identified threat actors, targets, or incident count. No workaround is available except disabling secondary authentication or patching immediately. Fixed versions: ASA 9.16.4.104, 9.18.4.96, 9.20.4.50, 9.22.3.200, and 9.23.1.48 for their corresponding release branches.

IETF approves STAMP extension for reflecting IP headers

IETF IESG · Oct 27, 2026 · Primary source

IESG approved draft-ietf-ippm-stamp-ext-hdr as Proposed Standard on October 27, 2026. Extension enables STAMP to reflect IPv4/IPv6 headers and IPv6 extension headers for end-to-end and hop-by-hop active measurements, including IOAM data field support.

Why it matters Extends STAMP measurement capability to capture IP header attributes and IOAM telemetry in production networks, improving performance validation and troubleshooting across network paths.

STAMP (Simple Two-Way Active Measurement Protocol, RFC 8762) is the basis for active network performance measurement in modern networks. This extension allows reflectors to capture and return IPv4/IPv6 headers and IPv6 extension headers from test packets, enabling operators to measure and validate IOAM (In Situ Operations, Administration, and Maintenance) data as packets traverse the network. This is critical for troubleshooting path-specific issues and validating hop-by-hop telemetry in segment routing, MPLS, and other modern network architectures. The extension updates RFC 8762 to define procedures for Session-Senders to include IP headers and for Session-Reflectors to reflect them back. This capability is essential for debugging network behavior and validating SLA compliance in complex multi-layer networks by correlating performance metrics with actual packet header contents and IOAM trace data during active measurement sessions.

VXLAN specification moves into the IETF document stream

IETF IESG · Oct 27, 2026 · Primary source

IESG approved draft-ietf-nvo3-rfc7348bis as Informational RFC on October 27, 2026. Moves deployed VXLAN protocol from Independent Submission to IETF document stream, enabling standardization of extensions and proper IANA code point allocation.

Why it matters Opens VXLAN to controlled standardization for forward extensions and interoperability governance through formal IETF standards process rather than vendor-driven approaches.

VXLAN (Virtual eXtensible Local Area Network) has been a de facto standard for overlay networks in data centers since RFC 7348 (2014), but as an Independent Submission lacked formal IETF management of extensions and IANA code points. This approval resubmits VXLAN as an IETF Informational RFC, enabling the NVO3 working group to coordinate extensions. Key technical benefit: allocation of proper IANA code points within the VXLAN header for future work—such as Group Policy Options and other encapsulation enhancements—that requires formal registry management. The 8-byte VXLAN header carries a 24-bit VNI (segment identifier), preserving all existing protocol semantics while establishing the framework for controlled extension development. For operators, this means future VXLAN enhancements will follow transparent standardization rather than proprietary extensions.
