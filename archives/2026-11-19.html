Puppet Enterprise RCE exploited one day after patch

DEV Community · Nov 19, 2026 · Industry news

CISA added CVE-2026-115731 to its KEV catalog November 17, confirming active exploitation of a deserialization flaw in Perforce Puppet; Perforce released fixes November 3, 2026. First public exploitation signals appeared November 4, one day after the patch.

Why it matters Puppet servers control certificate generation and infrastructure configuration across thousands of enterprises. Unpatched servers may have compromised CA signing keys, requiring immediate key rotation and audit trail review.

CVE-2026-115731 affects Perforce Puppet Enterprise 2026.0.0 before 2026.0.1, Puppet Enterprise 2025.12.x before 2025.12.1, Puppet Enterprise 2023.8.x before 2023.8.13, Puppet Core 9.x before 9.1.3, and Puppet Core 8.x before 8.22.2. The vulnerability allows unauthenticated remote code execution via unsafe deserialization in the Puppet server's report-processing code. An attacker reaching an unpatched Puppet server can execute arbitrary code with the privileges of the Puppet daemon, typically root. The timeline is aggressive: October 29–31 attackers found the flaw; Perforce released patches November 3; public proof-of-concept and exploitation appeared November 4. By November 17 (14 days post-patch), CISA confirmed active exploitation. Organizations running any of the affected versions face immediate risk. Mitigations: (1) Apply Perforce patches immediately via official channels; (2) audit Puppet server access logs for suspicious activity and failed authentication attempts from November 3 onward; (3) assume any Puppet Enterprise instance reachable before patching may have its CA keys compromised—generate new signing certificates and audit the certificate transparency logs for unexpected issuance; (4) review deployed Puppet manifests on all nodes for injected backdoors or configuration changes.

Attackers chain PAN-OS flaws with kernel exploit for root

The Hacker News · Nov 19, 2026 · Industry news

Palo Alto Networks confirmed attackers exploiting CVE-2026-109618 and CVE-2026-109619 (PHP2Shell) against PAN-OS management interfaces exposed to the internet; both flaws allow unauthenticated code execution on the web server. An attacker chained PHP2Shell with a Linux kernel flaw to gain root on 25 systems.

Why it matters Network infrastructure teams must immediately restrict firewall and VPN appliance management interfaces to internal networks only. Attackers achieved root access on critical appliances across multiple countries.

PHP2Shell vulnerabilities (CVE-2026-109618 and CVE-2026-109619) are critical remote code execution flaws in PHP that allow any unauthenticated attacker to execute arbitrary code on web servers. Palo Alto Networks confirmed active exploitation in late October 2026 targeting internet-exposed PAN-OS management interfaces on PA-Series and VM-Series firewalls and Panorama. The attack pattern: (1) unauthenticated attacker reaches management interface; (2) exploits PHP2Shell to execute shell commands on the firewall; (3) chains the exploit with CVE-2026-46300 (Fragnesia, a Linux kernel privilege escalation flaw) to escalate from web process user to root. Israeli security firm Dream found the attacker had reverse-engineered PAN-OS firmware, extracted PHP libraries, and built precise memory profiles for nine software versions. The confirmed victims (24 firewalls, 1 Panorama server) span four countries, indicating broad targeting. Recommended actions: (1) immediately remove internet access to firewall and network appliance management interfaces; (2) restrict management console access to defined trusted internal IP addresses via firewall rules; (3) assume any exposed management interface was compromised—scan for backdoors, review firewall logs and admin activity, check for configuration changes or new user accounts; (4) patch all Palo Alto, Cisco, Fortinet, and other appliances with published PHP2Shell mitigations; (5) deploy WAF or IPS rules to block exploitation attempts.

ExtraHop says agent zero trust needs network traffic analysis

ExtraHop · Nov 19, 2026 · Primary source

ExtraHop published guidance on Zero Trust architecture for autonomous agents: network traffic analysis is required to inventory agents, monitor MCP server connections, and prevent unauthorized lateral movement. Single prompt injections can steer agents into cross-segment access under valid credentials without triggering identity alarms.

Why it matters Network operators must add agent discovery and MCP connection monitoring to zero-trust implementations; network packets reveal agent behavior that endpoint and log-based telemetry miss, closing visibility gaps that allow rogue agents to pivot.

ExtraHop's November 19 analysis reframes zero trust for the agentic enterprise. Traditional zero trust relies on identity (IAM), endpoints, and logs, but agents operate under valid credentials and legitimate encrypted protocols—erratic agent calls blend into routine application traffic. Logs don't record agent execution unless explicitly instrumented, and endpoint software cannot observe AI processes running on other systems. Network traffic, however, is an unbypassable runtime record: every MCP call, API invocation, and data retrieval leaves a trace. By analyzing traffic patterns, operators can inventory agents (tracking which systems are calling infrastructure APIs), identify unauthorized MCP server connections, and detect anomalies like lateral movement across segmented networks. A single prompt injection hidden in a support ticket or email can redirect an agent to read sensitive records or cross network boundaries using existing credentials. Network-based detection catches these behaviors because traffic patterns diverge from baseline, even though IAM and audit logs see only valid operations. The post argues zero trust architecture must extend beyond users and endpoints to treat autonomous agents as network subjects requiring continuous monitoring, inventory, and behavioral analytics.

IETF updates DetNet TCQF and gLBF data plane drafts

IETF Datatracker · Nov 15, 2026 · Primary source

IETF Deterministic Networking working group updated draft-ietf-detnet-tcqf-03 and draft-ietf-detnet-glbf-04. TCQF targets low end-to-end jitter and hardware implementation ease; gLBF provides hop-by-hop forwarding with bounded latency without network-wide synchronization.

Why it matters DetNet latency guarantees are critical for mission-critical applications; these standards affect how you design real-time network paths for industrial automation and autonomous systems.

The IETF Deterministic Networking working group advanced two complementary data-plane mechanisms for bounded, predictable latency. TCQF (Tagged Cyclic Queuing and Forwarding) uses periodic queuing cycles to ensure low jitter; it scales to large networks via DiffServ aggregation and works with arbitrary link speeds and latency variations. gLBF (guaranteed Latency Based Forwarding) is an alternative hop-by-hop scheme based on Urgency-Rate-Latency calculus that doesn't require network-wide time synchronization. Both drafts now have matured to revision 3–4, indicating stabilization within the working group. These mechanisms are essential for deterministic latency in wide-area networks, automotive in-vehicle networks, and industrial IoT deployments. Practitioners implementing DetNet should track these standards; expect eventual RFCs within 2–4 quarters if current review pace holds.

The EU's December 2 enforcement deadline creates immediate compliance obligations for organizations using or deploying AI in European jurisdictions. Although some high-risk AI system requirements have been pushed to December 2027 and August 2028, enforcement bans on AI-generated non-consensual deepfakes and child sexual abuse material take effect December 2, 2026. This requires technical safeguards in content moderation, watermarking, and potentially redaction of training data. In parallel, AI companies are introducing new safety measures to control model and agent use, including limiting access to sensitive tools, setting clear permissions, and improving information storage practices. The simultaneous regulatory enforcement and vendor-driven access controls signal a shift in the industry toward default-restrictive architectures. Organizations must review existing AI tools, audit content safeguards, and implement technical marking rules. For infrastructure teams, this means supporting authentication and permission boundaries for agents accessing third-party systems, plus audit logging for sensitive operations.
