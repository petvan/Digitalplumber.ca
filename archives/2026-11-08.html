Local services fail when subsea cables cut hidden dependencies

APNIC Blog · Nov 5, 2026 · Analysis

When international links fail, hidden dependencies can take local services with them. Based on INNOG 9 findings, the post highlights services that fail during subsea cable outages because they depend on infrastructure outside the local economy, and recommends strengthening local DNS infrastructure and identifying external dependencies before the next outage occurs.

Why it matters Network operators should audit which locally-delivered services fail when international connectivity drops, then reduce external dependencies—a practical checklist for building true infrastructure resilience.

During international connectivity loss (subsea cable repair, geopolitical shutdown, or routing failure), local services often fail even though the local network remains intact. Examples: DNS resolvers hosted outside the country, cloud-based application components, remote APIs, time synchronization systems, and mobile payment platforms. Services that could otherwise continue operating locally may fail because they depend on infrastructure outside the economy. Recommendations focused on reducing these external dependencies, including strengthening local DNS infrastructure and planning for extended outages.

The author illustrates this with a July 2024 Internet shutdown experience where it became impossible to distinguish which tools had failed due to network unavailability versus those that had failed because they relied on systems outside the country. During repair work on SEA-ME-WE 5 in April 2026, users experienced slower connectivity and some interruptions, while SEA-ME-WE 4 remained in service. For operators, the post recommends: identify services that depend on infrastructure outside the economy, deploy appropriate local DNS infrastructure, and test how services behave when international connectivity is unavailable.

eMudhra intermediate CA keys generated with three bits entropy

eMudhra official statement; Google, Apple, Mozilla browser root program updates · Nov 5, 2026 · Primary source

Eight intermediate CAs operated by eMudhra had their private keys compromised with catastrophically weak entropy—as few as 3 bits instead of the required 384 bits for NIST P-384. Google Chrome and Mozilla Firefox set SCTNotAfter of November 16, 2026; Apple set G1 removal for November 30, 2026.

Why it matters TLS traffic encrypted with eMudhra certificates is trivially decryptable; infrastructure teams must identify affected certificates and plan immediate replacements before browser distrust dates—especially for enterprise VPN and load balancers.

In October 2026, security researchers discovered that Indian Certificate Authority eMudhra Limited issued eight intermediate TLS certificates bearing guessable private keys—one famously just the digit 4. Instead of the required 384-bit P-384 keys, some had as few as 3 bits of entropy. OffSec researchers confirmed the eight P-384 keys were recoverable by testing fewer than 256 candidate values, enabling adversary-in-the-middle attacks on any TLS session anchored to those certificates. Google Chrome will no longer trust TLS server authentication certificates validating to emSign Root CA - G1 whose earliest Signed Certificate Timestamp (SCT) is dated after November 16, 2026 11:59:59 PM UTC in Chrome 153 and higher. Certificates with SCT on or before that date remain unaffected. Infrastructure teams running eMudhra certificates must audit their PKI, identify affected intermediates, and migrate to replacement CAs before browser distrust dates. eMudhra announced withdrawal from the SSL/TLS business. This represents a systemic PKI supply-chain failure requiring immediate inventory and remediation across all network edge appliances, VPNs, and load balancers.

IETF publishes RFC 10069 for multipath QUIC connections

IETF RFC Editor · Nov 9, 2026 · Primary source

RFC 10069 specifies a multipath extension for QUIC enabling simultaneous usage of multiple paths for a single connection. After handshake indicating multipath support, endpoints can use multiple paths; the extension enables clients to open new paths independently.

Why it matters Multipath QUIC is now a Proposed Standard, enabling load balancing and failover across heterogeneous paths without application changes or OS kernel modifications—critical for mobile and edge-cloud traffic engineering.

Each path maintains distinct packet number states for sending and receiving packets. Senders manage per-path congestion status independently using standard QUIC congestion control mechanisms. Multiple paths can be used simultaneously, though no guarantee of full disjoint paths exists. Path IDs are monotonically increasing and never reused after abandonment. For operations practitioners, multipath QUIC enables automatic failover and bandwidth aggregation without application-level changes. Per-path congestion control is essential for WAN optimization over heterogeneous links (lossy cellular + low-latency terrestrial). The standard handles NAT rebinding and address migration transparently, reducing complexity in mobile and multi-cloud scenarios. Implementations treat path management as transport-layer concern, leaving application code unchanged. Transport parameter negotiation enables incremental deployment. Cipher suites with nonces shorter than 12 bytes cannot be used with multipath extension.

OTel-Arrow phase two cuts telemetry pipeline network overhead

OpenTelemetry Blog · Nov 5, 2026 · Primary source

OTel-Arrow Phase 2 extends OTAP transport protocol with the OTel-Arrow Dataflow Engine, a Rust runtime using OTAP as primary in-pipeline representation. Demonstrates significantly lower network overhead while preserving OpenTelemetry data model compatibility.

Why it matters Arrow-based OTAP pipelines achieve roughly 20x throughput improvement over OTLP in benchmarks; format conversion consumes majority of Collector CPU time, not processing logic. This cuts observability pipeline infrastructure costs and enables higher-cardinality telemetry without backend cost explosion.

OTAP reduces cost of representing telemetry by adopting columnar format (Apache Arrow) instead of row-oriented protobuf. The OTel-Arrow Dataflow Engine preserves compression advantage through processing and scales across cores while keeping overload behavior visible and contained. For production telemetry pipelines, that predictability matters as much as raw throughput. In row-oriented OTLP paths, telemetry arrives as protobuf bytes requiring deserialization-reserialization cycles; with OTAP-native paths, telemetry remains in Arrow record batches. This eliminates repeated format conversion, a hidden tax that compounds as telemetry volume increases. Phase 1 established OTAP representation and compression performance gains; Phase 2 delivers OTAP Dataflow Engine demonstrating column-oriented Arrow-based pipelines at production scale. SRE and AIOps teams can now run high-throughput observability infrastructure with lower CPU and memory footprint, enabling processing of richer telemetry before reaching backends.
