1.6T Ethernet arrives with linear and co-packaged optics

The Network DNA · Oct 16, 2026 · Analysis

The biggest engineering challenge is power and reach, which is why 1.6T is arriving alongside linear pluggable optics (LPO), co-packaged optics (CPO), and advanced silicon photonics. IEEE 802.3dj targeted for completion in 2026, with 1.6T-capable NICs shipping with next-gen accelerators and hyperscaler and neocloud 1.6T spine deployments beginning.

Why it matters A 1.6T port translates to fewer cables, fewer optics, fewer switch tiers, and lower latency per bit moved inside an AI cluster. Network practitioners sizing AI infrastructure can now plan 1.6T deployments as a proven scaling path beyond 800G constraints.

1.6T Ethernet delivers 1,600 Gb/s per port (double 800G), standardized by IEEE 802.3dj with electrical interfaces aligned to OCI CEI-224G, using 200 Gb/s per lane with PAM4 modulation over 8 lanes. Expected milestones include 102.4T switch ASICs announced and sampling in 2025 with first 1.6T DSP pluggable and LPO modules, first CPO switch systems unveiled, and 800G in volume for AI fabrics; in 2026, IEEE 802.3dj targeted for completion, 1.6T-capable NICs shipping with next-gen accelerators, and hyperscaler and neocloud 1.6T spine deployments beginning. Ultra Ethernet (UEC) runs as a transport-layer specification on top of 800G and 1.6T physical layers and is a major reason hyperscalers are confident standardizing AI fabrics on Ethernet. The analysis covers form factors (OSFP-XD leading for 1.6T), cabling strategies (single-mode OS2 fiber for longer-reach links), and deployment timeline showing 800G as the current workhorse with 1.6T early sampling transitioning to broader adoption as the 802.3dj standard finalizes.

IETF advances ASPA based BGP AS_PATH verification draft

IETF · Oct 16, 2026 · Primary source

The IETF SIDROPS working group published version 29 of the ASPA verification draft, which describes procedures to verify BGP AS_PATH attributes using ASPA objects in RPKI, enhancing routing security by detecting and mitigating route leaks and AS_PATH manipulations.

Why it matters Network operators need ASPA specifications to mature from Internet-Drafts to RFC status to enable production deployment of path-validation tools and achieve route-leak detection beyond origin-only validation.

The ASPA-based AS_PATH verification Internet-Draft (version 29, published October 16, 2026) describes how operators can use Autonomous System Provider Authorization (ASPA) objects alongside ROAs to verify the full AS path in BGP announcements. While ROAs validate only whether an origin AS is authorized to announce a prefix, ASPA adds cryptographic verification that traffic follows authorized AS paths, closing a major gap in routing security. The draft defines validation procedures to detect route leaks (where legitimate routes propagate beyond policy) and AS_PATH manipulations. This document is advancing through the IETF SIDROPS working group; at press time, the profile, verification algorithm, and RPKI-to-Router (RTR) protocol v2 remain Internet-Drafts rather than finalized RFCs, meaning operators can publish ASPA objects now (already available in RIPE NCC, ARIN, and APNIC portals) but should monitor validation states before enforcing drop policies on routers. The specification update is part of a phased industry push toward mandatory provider-list publication across all five RIRs by end of 2026.

eMudhra intermediate CA private keys recoverable in under a second

Red Hat Security Advisory (RHSB-2026-012) · Oct 21, 2026 · Primary source

On October 17, 2026, researchers identified cryptographic weakness affecting eight eMudhra intermediate certificates: six for TLS validation and two for code signing. Each P-384 private key was below 256, recoverable in under a second.

Why it matters Attackers possessing these keys can forge TLS certificates for any domain, enabling man-in-the-middle interception of encrypted traffic. All infrastructure using mTLS, API authentication, or affected trust chains must audit and revoke trust immediately.

A security researcher identified the compromise on October 17 and demonstrated possession of private keys by submitting valid signed attestations to browser root programs and eMudhra. Six impacted certificates were for TLS trusted by Apple, Chrome, Microsoft and Mozilla; two were code-signing certificates trusted by Microsoft. Browsers blocked the affected intermediates using revocation lists, but most non-browser software lacks intermediate CA revocation filtering, forcing many projects to remove the emSign ECC Root CA - G3 from their roots of trust. Chrome and Firefox blocked on October 17, Apple on October 19, Microsoft on October 20. Apps, servers and devices without revocation updates may still trust the compromised certificates, exposing traffic to interception. Network teams must audit certificate chains in load balancers, API gateways, mutual TLS configurations, and embedded trust stores.

Node.js patches Brotli RCE and TLS hostname bypasses

Astra Security · Oct 21, 2026 · Primary source

Node.js released security updates for versions 26.x, 24.x, and 22.x on October 21, 2026, fixing 10 CVEs including CVE-2026-111497, a Brotli decoder out-of-bounds write enabling remote code execution, plus TLS hostname/IP bypasses and DNS NUL truncation flaws.

Why it matters Brotli RCE is remotely exploitable on any Node.js instance handling compressed HTTP. TLS and DNS fixes prevent encryption-layer bypasses. All infrastructure using Node.js for APIs, services, or network tooling must patch immediately.

The release fixes 10 CVEs across core engine and bundled dependencies including c-ares, OpenSSL, SQLite, and Undici, plus ships an updated CA certificate store to address the eMudhra intermediate CA compromise. CVE-2026-111497 is an out-of-bounds write in Brotli decompression—critical because Brotli is ubiquitous in HTTP compression. TLS fixes address hostname validation bypass and DNS fixes cover NUL truncation edge cases that could allow protocol bypasses in edge cases. The eMudhra CA store update is essential to prevent reliance on compromised intermediates. All versions (26.x, 24.x, 22.x) receive c-ares and Undici updates; 24.x and 22.x receive OpenSSL updates; 22.x receives SQLite updates. Teams must test and deploy across all Node.js infrastructure.

AI SRE agent key compromises average $13 million per incident

AI Journal · Oct 23, 2026 · Analysis

Security analysis of 2026 AI SRE agent deployments reveals operational infrastructure as the costliest attack surface, with key compromise averaging $13M+ per incident. Examines governance gaps when agents hold administrative credentials.

Why it matters Operations teams deploying AI agents with infrastructure access must implement governance primitives—audit trails, rollback paths, permission models—before granting autonomy, not after.

The article exposes a critical gap between agent capability and operational readiness in production SRE deployments. Early 2026 incidents showed that while agents accelerate diagnosis and remediation, giving them keystroke access without mature governance layers created new attack surfaces. Key finding: most losses came through operations (key compromise, credential exposure, permission misuse) rather than agent reasoning errors. The analysis argues infrastructure teams must implement timelocks, length-prefixed encodings, and consumed references—defensive primitives from formal verification and blockchain—before agents hold infrastructure keys. This represents a governance reset: agent frameworks handle orchestration, but operational safety requires controls external to the agent itself. Essential reading for operations and SRE leads considering autonomous remediation and moving agents from advisory to autonomous change mode.

IPinfo leads rivals on IPv4 geolocation accuracy, study finds

arXiv · Oct 19, 2026 · Research

Six-month longitudinal analysis of RIPE Atlas latency measurements against four geolocation providers reveals consistent but provider-specific accuracy patterns. IPinfo leads DB-IP by 5.4 percentage points for IPv4, while MaxMind shows 10.7 percentage point degradation for IPv4 routers versus general addresses.

Why it matters Operations teams using geolocation for CDN steering, DDoS mitigation, or compliance must audit provider choice against actual network topology; accuracy varies significantly by address type and protocol version.

This longitudinal study evaluates consistency between RIPE Atlas latency measurements and location estimates from DB-IP, IP2Location, IPinfo, and MaxMind as a proxy for geolocation quality. The study analyzed six months of data (January-June 2026) covering 2.6+ billion measurements across 5+ million unique IPs. Key finding: consistency is stable over time but varies greatly by provider and IP type. For IPv4 routers, MaxMind is 10.7 percentage points worse than general case while IPinfo is only 1.6 percentage points worse; for IPv6, routers are geolocated more consistently than non-routers by all providers. This matters for operators using geolocation for traffic steering, compliance checks, or fraud detection; relying on a single provider without understanding these patterns risks misclassifying traffic or missing legitimate regional users.
